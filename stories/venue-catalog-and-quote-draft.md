## 零、這一輪在做什麼

把家具從「9 種寫死的類型」變成「**可查詢、有價格、有分類的目錄**」,並讓使用者在畫圖的同時看到累計金額。

這是產品定位的轉折:目前的規劃器交付的是**圖**,加上報價之後交付的是**決策依據**。競品 233 個品項全部帶 NT$ 定價,那才是它存在的理由 —— 畫得漂亮是手段,知道要花多少錢是目的。

## 一、核心架構決議

### D1:`FurnitureItem` 只存 `code`,分類由目錄查出

```ts
// 現在
FurnitureItem { id, kind: FurnitureKind, center, w, h, rotationDeg }

// 之後
FurnitureItem { id, code: string, center, rotationDeg }
```

分類、尺寸、價格、幾何來源**全部查目錄**。

**為什麼不把分類也存在 item 上**:兩個欄位描述同一件事就可能不一致 —— `kind:"table"` 配 `code:"CHR-3"`,然後 2D 依 kind 畫、3D 依 code 畫,同一件家具兩個畫面不同東西。要「並存」的是**概念**不是**欄位**:分類是查出來的,所以不可能跟品項打架。

**順手解掉一個既存不一致**:現在 `FurnitureItem` 自己存 `w`/`h`(建立當下的快照),但 `height3d` 每次現查 `FURNITURE_DEFAULTS`,而且 2D 用 `item.w/h`、GLB 與程序化路徑用 `FURNITURE_DEFAULTS[kind].w/h`。改了那張表,舊存檔的家具會在 2D 是舊尺寸、3D 是新尺寸。改成只存 code 之後所有尺寸單一來源,這個坑自動消失。

### D2:三層分類

```
大類(A 展示設備)
└── 子類(A1 方形展台)
    └── 品項(桌子 100×50×H75 / NT$650)
```

比照競品。UI 的目錄頁靠這個階層做導覽與篩選。

### D3:代碼自己編

現階段沒有真實廠商型錄,代碼由我們定(如 `TBL-100-75`)。欄位形狀照未來廠商資料設計,拿到真型錄時換的是資料不是結構。

### D4:方正規格件走程序化,造型件才用開源模型

| 幾何來源 | 適用 | 理由 |
|---|---|---|
| **程序化參數化** | 展台、桌子、櫃子、櫃檯、講台、層板 | 本來就是方箱體。尺寸 100% 精確、變體無限、零下載。競品 233 項全是這種 |
| **開源 GLB** | 椅子、沙發、植栽 | 有曲面,方箱畫不出來 |

**這一條解決了目錄最難的矛盾**:目錄要有「桌子 H75」和「桌子 H100」兩個品項,但開源模型一款只有一種尺寸。等比縮放縮不出兩種正確比例,非等比拉伸又違反既有硬規定(而且拉伸的椅腳很難看)。程序化幾何沒有這個問題 —— 尺寸就是參數。

**家具尺寸仍然不可調**(維持既有硬規定)。使用者不是把桌子拉高,是**選另一個型號** —— 這比競品的 scale gizmo 更貼近實務,現實中租不到「拉高 13% 的桌子」。

### D5:目錄放程式碼常數,欄位照廠商資料形狀

`src/lib/venue/catalog.ts`,純領域模組(零 React / Three / DOM)。

```ts
interface CatalogItem {
  code: string;          // "TBL-100-75"
  name: string;          // "桌子 100×50×H75"
  spec: string;          // "Info Counter"(英文規格名,對廠商溝通用)
  category: string;      // "A"
  subCategory: string;   // "A1"
  w: number;             // 公尺
  d: number;
  height3d: number;
  price: number;         // 未稅單價
  currency: "TWD";
  supplier: string | null;   // 現階段 null
  geometry:
    | { kind: "procedural"; shape: ProceduralShape; params: … }
    | { kind: "model"; url: string; rotationY: number; deferred: boolean };
  color: string;
}
```

換成 API 只要換載入來源,消費端不動。

### D6:報價先只做小計

品項單價 × 數量 → 小計。**稅率與人員時薪之後再說** —— 先驗證「畫圖時看得到累計金額」這件事有沒有用。

### D7:可編輯範圍 = 攤位尺寸 + 5m 邊距

取代固定的 `PLAN_AREA_SIZE_M = 200`。3×3 攤位 → 約 13×13m 畫布;9×3 → 約 19×13m。

邊距當暫存區,重排時可以先把東西挪出攤位。換尺寸時邊距區的物件可能被擠出去 —— 沿用第二輪 T6 那套確認對話框。

### D8:舊存檔作廢

沿用第二輪決議。`kind` → `code` 是破壞性變更,不寫遷移。

## 四、競品對照(供實作時參考)

分析對象:`douni-syun-boothcraft.lovable.app`,7.3MB 單一 HTML,Three.js r128,233 個品項。

**它領先的**:報價(233 項定價 + 人員時薪 + 稅率)、目錄深度、GLB 匯出、四面牆各自貼圖、物件間磁吸(12cm 吸附 / 22cm 脫離)、undo/redo、群組、autosave、navisphere。

**我們領先的**:TypeScript strict + 分層架構 + 30 支 spec/8484 行測試、真實 PBR 材質與陰影、AI 助理、步驟 02/03 分離。

**它的攤位預設**(印證第二輪 T6 方向正確):
```
半攤 3×1.5 / 標準攤位 3×3 / 雙攤 6×3 / 三攤 9×3
```
自訂上限 3000cm。我們多了 6×6,少了半攤 3×1.5 —— 可考慮補上,並改用產業術語當標籤。

**不採用它的部分**:它的 3D 資產與價目表沒有授權聲明,不會取用。我們的 Poly Haven CC0 管線品質更高且來源清楚。要學的是「尺寸與型號的產業慣例」(展台有 50/75/100cm 三種標準高度、桌子 100×50 是基本模組),那是產業知識不是誰的著作,查搭建廠商公開型錄即可。

## 五、驗收標準

每個 task 開工前先把這些寫成可執行的 Playwright 檢查項,**先讓它失敗**,實作後才通過。

第二輪學到的教訓直接套用:**檢查項要讀實作「產出」的東西,不是實作「回報」的東西。** 那一輪三次「測試全綠但實作已經壞掉」,全是守衛在讀 prop 的回音、或讀一個兩條路徑都相同的數字。下面凡是容易寫成空守衛的地方都標了。

### T1 可編輯範圍 = 攤位 + 5m 邊距

1. 預設 3×3 攤位時 `data-plan-area-m` 為 `13`(3 + 5×2)
2. 套用 9×3 preset 後,可編輯範圍隨之變成 `19 × 13`(長短邊分開)
3. 柱子拖到範圍外會被夾在邊界上,不會跑到 200m 外
4. 家具同上
5. 地板頂點同上
6. **格線數量跟著降** —— 探針回報的格線條數在 3×3 攤位時遠少於改動前(舊值是每軸 200 條)
7. `grep -rn "PLAN_AREA_SIZE_M" src/` 無結果(常數已移除,不是留著沒人用)
8. 邊距區可放物件:攤位外 2m 處放得下柱子,但 6m 處放不下
9. **破壞驗證**:把夾制改回固定 200 → 第 3、4 項應失敗

### T2 目錄資料層

1. `CATALOG` 至少含 9 個品項,對應現有 9 種家具
2. 每個 `code` 唯一(以程式檢查,不是人工看)
3. 每個品項的 `category` / `subCategory` 都能在分類表中找到 —— **沒有孤兒分類**
4. 每個品項的 `geometry` 不是 `procedural` 就是 `model`,且 `model` 指向的 GLB 檔案實際存在(打 HTTP 200)
5. `FurnitureItem` 型別上**沒有** `kind` / `w` / `h` 欄位(以型別檢查,`tsc` 會擋)
6. 放置一件家具後,`data-furniture` 裡的物件只有 `id` / `code` / `center` / `rotationDeg`
7. **破壞驗證**:給兩個品項相同的 code → 第 2 項應失敗

### T3 繪製路徑改吃目錄

1. 2D 畫出的家具尺寸 = `CATALOG[code].w` × `CATALOG[code].d`
2. 步驟 02 探針量到的實際 mesh 尺寸與 catalog 宣告一致(誤差 < 1cm)
3. 步驟 03 同上
4. **單一來源檢查(這一項是 T3 的重點)**:把 catalog 裡某品項的尺寸改掉,2D 與 3D **同時**變成新尺寸。改動前的架構會讓 2D 變、3D 不變 —— 這正是 D1 要消滅的不一致
5. 模型快取以 `code` 為鍵,往返步驟 03 三趟後 `totalBuilds` 不增加
6. 探針的家具分組鍵改成 `code`,同一大類的不同品項各自分開計數
7. **破壞驗證**:讓 3D 路徑改讀寫死的尺寸表 → 第 4 項應失敗

### T4 AI schema 改用 code

1. AI 回傳合法 `code` → 家具正確放置
2. AI 回傳**不存在的 code** → 不新增家具,且面板顯示明確錯誤(比照既有「已跳過刪除」的訊息模式)
3. 該錯誤不會讓整批 actions 中斷 —— 同一批裡合法的那些仍然套用
4. tool schema 裡**沒有**品項代碼的 enum(以原始碼檢查)—— 目錄會長大,enum 會隨之改動並破壞 prompt cache
5. system prompt 仍是凍結字串,未因目錄而插值(比照 AGENTS.md 既有硬規定)
6. **破壞驗證**:拿掉代碼驗證 → 第 2 項應失敗

### T5 方正規格件改程序化

1. 同款不同高度的兩個品項(如 `TBL-100-75` / `TBL-100-100`)實際 mesh 高度分別為 0.75m 與 1.00m,**誤差 < 1cm**
2. 兩者的水平尺寸相同(同款只有高度不同)
3. 程序化品項**不發出任何 GLB 請求**
4. 造型件(椅/沙發/植栽)仍走 GLB,且維持等比縮放(三軸縮放倍率相同)
5. 家具仍不可縮放:場上選取家具時無縮放把手,`TransformControls` 只有 translate / rotate
6. **破壞驗證**:把程序化品項的高度參數寫死 → 第 1 項應失敗

### T6 擴充目錄與價格

1. 三層結構完整:每個大類至少一個子類,每個子類至少一個品項
2. 每個品項 `price` 為正數(demo 資料也不能是 0,否則報價驗不出來)
3. `currency` 一律 `"TWD"`
4. 目錄總數與分類統計可由程式取得,供 UI 與測試共用
5. 所有 `geometry.kind === "model"` 的 GLB 檔案都存在
6. **破壞驗證**:加一個 `subCategory` 指向不存在大類的品項 → 第 1 項應失敗

### T7 家具目錄頁 UI

1. 三層導覽可用:點大類展開子類,點子類列出品項
2. 品項卡顯示名稱、尺寸、價格
3. 搜尋輸入「桌」能同時命中不同子類下的桌類品項
4. 搜尋輸入不存在的字串 → 顯示「無結果」,不是空白畫面
5. 點品項後進入放置模式,點地板即放上該 `code` 的家具
6. **尺寸不可調**:品項卡與屬性面板都沒有寬/高輸入框,場上也沒有縮放把手
7. 目錄頁不影響既有的步驟 01/02/03 行為
8. **破壞驗證**:讓搜尋只比對品項名開頭 → 第 3 項應失敗

### T8 報價小計

1. 空場地時小計為 0
2. 放一件 NT$650 的品項 → 小計 650
3. 再放一件 NT$700 → 小計 1350(**加總,不是取代**)
4. 刪除其中一件 → 小計回到正確值
5. 小計數字來自 `CATALOG[code].price` 逐件加總,與場上實際件數一致 —— 以探針回報的件數交叉驗證,不是只讀畫面數字
6. 明細列出每個品項的名稱、數量、單價、小計
7. **破壞驗證**:把加總改成「只算第一件」 → 第 3 項應失敗
