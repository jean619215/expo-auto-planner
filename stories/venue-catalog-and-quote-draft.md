> 來源:使用者四條需求 + 競品分析(douni-syun-boothcraft,展覽攤位空間模擬器)。

## 零、這一輪在做什麼

把家具從「9 種寫死的類型」變成「**可查詢、有價格、有分類的目錄**」,並讓使用者在畫圖的同時看到累計金額。

這是產品定位的轉折:目前的規劃器交付的是**圖**,加上報價之後交付的是**決策依據**。競品 233 個品項全部帶 NT$ 定價,那才是它存在的理由 —— 畫得漂亮是手段,知道要花多少錢是目的。

## 一、核心架構決議

### D1:`FurnitureItem` 只存 `code`,分類由目錄查出

```ts
// 現在
FurnitureItem { id, kind: FurnitureKind, center, w, h, rotationDeg }

// 之後
FurnitureItem { id, code: string, center, rotationDeg }
```

分類、尺寸、價格、幾何來源**全部查目錄**。

**為什麼不把分類也存在 item 上**:兩個欄位描述同一件事就可能不一致 —— `kind:"table"` 配 `code:"CHR-3"`,然後 2D 依 kind 畫、3D 依 code 畫,同一件家具兩個畫面不同東西。要「並存」的是**概念**不是**欄位**:分類是查出來的,所以不可能跟品項打架。

**順手解掉一個既存不一致**:現在 `FurnitureItem` 自己存 `w`/`h`(建立當下的快照),但 `height3d` 每次現查 `FURNITURE_DEFAULTS`,而且 2D 用 `item.w/h`、GLB 與程序化路徑用 `FURNITURE_DEFAULTS[kind].w/h`。改了那張表,舊存檔的家具會在 2D 是舊尺寸、3D 是新尺寸。改成只存 code 之後所有尺寸單一來源,這個坑自動消失。

### D2:三層分類

```
大類(A 展示設備)
└── 子類(A1 方形展台)
    └── 品項(桌子 100×50×H75 / NT$650)
```

比照競品。UI 的目錄頁靠這個階層做導覽與篩選。

### D3:代碼自己編

現階段沒有真實廠商型錄,代碼由我們定(如 `TBL-100-75`)。欄位形狀照未來廠商資料設計,拿到真型錄時換的是資料不是結構。

### D4:方正規格件走程序化,造型件才用開源模型

| 幾何來源 | 適用 | 理由 |
|---|---|---|
| **程序化參數化** | 展台、桌子、櫃子、櫃檯、講台、層板 | 本來就是方箱體。尺寸 100% 精確、變體無限、零下載。競品 233 項全是這種 |
| **開源 GLB** | 椅子、沙發、植栽 | 有曲面,方箱畫不出來 |

**這一條解決了目錄最難的矛盾**:目錄要有「桌子 H75」和「桌子 H100」兩個品項,但開源模型一款只有一種尺寸。等比縮放縮不出兩種正確比例,非等比拉伸又違反既有硬規定(而且拉伸的椅腳很難看)。程序化幾何沒有這個問題 —— 尺寸就是參數。

**家具尺寸仍然不可調**(維持既有硬規定)。使用者不是把桌子拉高,是**選另一個型號** —— 這比競品的 scale gizmo 更貼近實務,現實中租不到「拉高 13% 的桌子」。

### D5:目錄放程式碼常數,欄位照廠商資料形狀

`src/lib/venue/catalog.ts`,純領域模組(零 React / Three / DOM)。

```ts
interface CatalogItem {
  code: string;          // "TBL-100-75"
  name: string;          // "桌子 100×50×H75"
  spec: string;          // "Info Counter"(英文規格名,對廠商溝通用)
  category: string;      // "A"
  subCategory: string;   // "A1"
  w: number;             // 公尺
  d: number;
  height3d: number;
  price: number;         // 未稅單價
  currency: "TWD";
  supplier: string | null;   // 現階段 null
  geometry:
    | { kind: "procedural"; shape: ProceduralShape; params: … }
    | { kind: "model"; url: string; rotationY: number; deferred: boolean };
  color: string;
}
```

換成 API 只要換載入來源,消費端不動。

### D6:報價先只做小計

品項單價 × 數量 → 小計。**稅率與人員時薪之後再說** —— 先驗證「畫圖時看得到累計金額」這件事有沒有用。

### D7:可編輯範圍 = 攤位尺寸 + 5m 邊距

取代固定的 `PLAN_AREA_SIZE_M = 200`。3×3 攤位 → 約 13×13m 畫布;9×3 → 約 19×13m。

邊距當暫存區,重排時可以先把東西挪出攤位。換尺寸時邊距區的物件可能被擠出去 —— 沿用第二輪 T6 那套確認對話框。

### D8:舊存檔作廢

沿用第二輪決議。`kind` → `code` 是破壞性變更,不寫遷移。

## 二、任務順序

全部依序,不平行(理由同第二輪:`PlanEditor.tsx` 是唯一 state owner,已 2234 行)。

| # | 內容 | 排序理由 |
|---|---|---|
| **T1** | 可編輯範圍改成「攤位 + 5m 邊距」,取代 `PLAN_AREA_SIZE_M` | 與目錄無關的獨立技術債,先清掉。動到頂點/柱子/家具的夾制與 `MIN_SCALE`,晚做會跟目錄改動糾纏 |
| **T2** | 建 `catalog.ts` 資料層,9 個 kind 遷移成 9 個品項 | 純資料與型別,不動 UI。地基 |
| **T3** | 繪製路徑改吃目錄:2D、白模輪廓、GLB、程序化、探針、快取 | `code` 取代 `kind` 當快取鍵與探針分組鍵 |
| **T4** | AI schema 改用 `code` + 不存在代碼的錯誤回饋 | schema 用自由字串 + 伺服器端驗證,不用 enum(目錄會長大,enum 會破壞 prompt cache) |
| **T5** | 方正規格件改程序化參數化幾何 | 讓「同款不同尺寸」真的可行 |
| **T6** | 擴充目錄:三層分類 + 品項與價格 | 資料工作為主 |
| **T7** | 家具目錄頁 UI(大類 → 子類 → 品項、搜尋),UIUX 近似競品 | 依賴 T6 的資料 |
| **T8** | 報價小計面板 | 依賴 T6 的價格 |
| **T9** | 模型貼皮(參考競品)—— **範圍未定,待細談** | 使用者列為最後階段 |

## 三、待決(T9 之前要談)

競品的「貼皮」有三項,還沒確認你要哪些:

1. **四面牆各自上傳貼圖**(競品有 front/back/left/right;你目前所有牆共用一組)

## 四、競品對照(供實作時參考)

分析對象:`douni-syun-boothcraft.lovable.app`,7.3MB 單一 HTML,Three.js r128,233 個品項。

**它領先的**:報價(233 項定價 + 人員時薪 + 稅率)、目錄深度、GLB 匯出、四面牆各自貼圖、物件間磁吸(12cm 吸附 / 22cm 脫離)、undo/redo、群組、autosave、navisphere。

**我們領先的**:TypeScript strict + 分層架構 + 30 支 spec/8484 行測試、真實 PBR 材質與陰影、AI 助理、步驟 02/03 分離。

**它的攤位預設**(印證第二輪 T6 方向正確):
```
半攤 3×1.5 / 標準攤位 3×3 / 雙攤 6×3 / 三攤 9×3
```
自訂上限 3000cm。我們多了 6×6,少了半攤 3×1.5 —— 可考慮補上,並改用產業術語當標籤。

**不採用它的部分**:它的 3D 資產與價目表沒有授權聲明,不會取用。我們的 Poly Haven CC0 管線品質更高且來源清楚。要學的是「尺寸與型號的產業慣例」(展台有 50/75/100cm 三種標準高度、桌子 100×50 是基本模組),那是產業知識不是誰的著作,查搭建廠商公開型錄即可。
