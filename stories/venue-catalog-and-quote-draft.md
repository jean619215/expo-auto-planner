# 家具目錄與報價（第三輪）—— 決議與任務順序

> **狀態:T1、T2 已完成;T3 實作完成、驗收尚未穩定(2026-08-25)。**
> 來源:使用者四條需求 + 競品分析(douni-syun-boothcraft,展覽攤位空間模擬器)。

## 零、這一輪在做什麼

把家具從「9 種寫死的類型」變成「**可查詢、有價格、有分類的目錄**」,並讓使用者在畫圖的同時看到累計金額。

這是產品定位的轉折:目前的規劃器交付的是**圖**,加上報價之後交付的是**決策依據**。競品 233 個品項全部帶 NT$ 定價,那才是它存在的理由 —— 畫得漂亮是手段,知道要花多少錢是目的。

## 一、核心架構決議

### D1:`FurnitureItem` 只存 `code`,分類由目錄查出

```ts
// 現在
FurnitureItem { id, kind: FurnitureKind, center, w, h, rotationDeg }

// 之後
FurnitureItem { id, code: string, center, rotationDeg }
```

分類、尺寸、價格、幾何來源**全部查目錄**。

**為什麼不把分類也存在 item 上**:兩個欄位描述同一件事就可能不一致 —— `kind:"table"` 配 `code:"CHR-3"`,然後 2D 依 kind 畫、3D 依 code 畫,同一件家具兩個畫面不同東西。要「並存」的是**概念**不是**欄位**:分類是查出來的,所以不可能跟品項打架。

**順手解掉一個既存不一致**:現在 `FurnitureItem` 自己存 `w`/`h`(建立當下的快照),但 `height3d` 每次現查 `FURNITURE_DEFAULTS`,而且 2D 用 `item.w/h`、GLB 與程序化路徑用 `FURNITURE_DEFAULTS[kind].w/h`。改了那張表,舊存檔的家具會在 2D 是舊尺寸、3D 是新尺寸。改成只存 code 之後所有尺寸單一來源,這個坑自動消失。

### D2:三層分類

```
大類(A 展示設備)
└── 子類(A1 方形展台)
    └── 品項(桌子 100×50×H75 / NT$650)
```

比照競品。UI 的目錄頁靠這個階層做導覽與篩選。

### D3:代碼自己編

現階段沒有真實廠商型錄,代碼由我們定(如 `TBL-100-75`)。欄位形狀照未來廠商資料設計,拿到真型錄時換的是資料不是結構。

### D4:方正規格件走程序化,造型件才用開源模型

| 幾何來源 | 適用 | 理由 |
|---|---|---|
| **程序化參數化** | 展台、桌子、櫃子、櫃檯、講台、層板 | 本來就是方箱體。尺寸 100% 精確、變體無限、零下載。競品 233 項全是這種 |
| **開源 GLB** | 椅子、沙發、植栽 | 有曲面,方箱畫不出來 |

**這一條解決了目錄最難的矛盾**:目錄要有「桌子 H75」和「桌子 H100」兩個品項,但開源模型一款只有一種尺寸。等比縮放縮不出兩種正確比例,非等比拉伸又違反既有硬規定(而且拉伸的椅腳很難看)。程序化幾何沒有這個問題 —— 尺寸就是參數。

**家具尺寸仍然不可調**(維持既有硬規定)。使用者不是把桌子拉高,是**選另一個型號** —— 這比競品的 scale gizmo 更貼近實務,現實中租不到「拉高 13% 的桌子」。

### D5:目錄放程式碼常數,欄位照廠商資料形狀

`src/lib/venue/catalog.ts`,純領域模組(零 React / Three / DOM)。

```ts
interface CatalogItem {
  code: string;          // "TBL-100-75"
  name: string;          // "桌子 100×50×H75"
  spec: string;          // "Info Counter"(英文規格名,對廠商溝通用)
  category: string;      // "A"
  subCategory: string;   // "A1"
  w: number;             // 公尺
  d: number;
  height3d: number;
  price: number;         // 未稅單價
  currency: "TWD";
  supplier: string | null;   // 現階段 null
  geometry:
    | { kind: "procedural"; shape: ProceduralShape; params: … }
    | { kind: "model"; url: string; rotationY: number; deferred: boolean };
  color: string;
}
```

換成 API 只要換載入來源,消費端不動。

### D6:報價先只做小計

品項單價 × 數量 → 小計。**稅率與人員時薪之後再說** —— 先驗證「畫圖時看得到累計金額」這件事有沒有用。

### D7:可編輯範圍 = 攤位尺寸 + 5m 邊距

取代固定的 `PLAN_AREA_SIZE_M = 200`。3×3 攤位 → 約 13×13m 畫布;9×3 → 約 19×13m。

邊距當暫存區,重排時可以先把東西挪出攤位。換尺寸時邊距區的物件可能被擠出去 —— 沿用第二輪 T6 那套確認對話框。

### D8:舊存檔作廢

沿用第二輪決議。`kind` → `code` 是破壞性變更,不寫遷移。

### T1 完成紀錄(2026-08-24)

九項驗收條件全數通過,破壞驗證(把夾制改回固定 200m 見方)有 7/8 轉紅
(第 8 項是 grep 常數,本來就該維持綠)。新 spec:`venue-plan-area.spec.ts`。

**實作時推翻的兩個規劃假設:**

1. **「可編輯範圍由目前地板多邊形推導」—— 不能這樣做。** 那會構成回饋迴圈:
   拖曳頂點讓地板變大 → 範圍跟著變大 → 更大的範圍允許把頂點拖得更遠。實測
   一次 8 步的拖曳就把 3m 攤位的地板拉到 63m 外。範圍必須錨在**使用者選定的
   攤位尺寸**(只在換 preset / 自訂尺寸 / 讀檔 / AI 重畫地板時更新),頂點的
   自由編輯在那圈邊距內活動。已寫進 `planAreaFor` 的註解。

2. **換攤位尺寸時,物件是夾進「可編輯範圍」而不是「攤位」。** D7 說邊距是暫存
   區,夾進攤位會把刻意放在暫存區的東西一起吸回去。`venue-booth-preset` 的
   三個案例因此要換座標:25 那一帶在 3×3 的可編輯範圍裡,不算超出。

**破壞驗證抓到兩個空守衛**(第五節那套方法確實有用):柱子拖曳與頂點拖曳原本
拿 `data-plan-area` 回報的範圍當比較基準,把實作改回固定 200m 之後**兩邊一起
漂移**,守衛照樣全綠。改成寫死預期邊界(15 / 28)才抓得到。

**既有測試的更新量比預期大。** 第六節只點名 `venue-objects` / `venue-zoom-pan`,
實際還動到 `venue-dimensions`、`venue-plan-editor`、`venue-booth-preset`、
`venue-3d-scene`、`venue-column-offsets`、`venue-refined-lighting`,以及九支
spec 裡共用的 `drawWall({x:5,y:5},{x:10,y:5})` 樣式 —— 那條牆現在兩端會被夾到
同一點而**根本不會被建立**,偏偏多數案例不斷言牆數,於是安靜地在一個沒有牆的
場景上繼續跑。這種「壞掉但還是綠」的破壞方式,下一個 task 動到座標系時要再查
一次。

免登入的 26 支 spec 最後結果:**241 通過、0 失敗**。

### T2 完成紀錄(2026-08-25)

七項驗收條件全數通過。破壞驗證做了三處(不只規定的第 7 項),全部精準轉紅:
重複代碼 → 第 2 項紅、其餘綠;GLB 路徑指向不存在的檔 → 第 4 項紅;把 `w`/`h`
加回品項 → 第 5、6 項同時紅。新 spec:`venue-catalog.spec.ts`。

**規劃時沒想到的三件事:**

1. **`catalog.ts` 不能 import `furniture.ts`。** 原案要讓目錄沿用
   `FURNITURE_DEFAULTS` 的數字以確保搬家不走樣,但那是執行期循環:`CATALOG`
   初始化時讀 `FURNITURE_DEFAULTS`,而後者的模組還沒求值完,直接撞 TDZ。方向
   改成相反 —— 尺寸字面量進目錄,`FURNITURE_DEFAULTS` 由目錄推導。結果比原案
   好:兩份數字不可能分岔,而不是靠人維持一致。`catalog.ts` 現在只依賴
   `models.ts`(取 `MODEL_BASE_PATH`),而後者對 `furniture.ts` 只有型別 import,
   執行期不成環。

2. **`tsc` 放行了一個真 bug。** `createFurniture(placingKind, …)` —— 參數從
   `FurnitureKind` 換成 `code: string` 之後,字串聯集對 `string` 完全相容,於是
   `"table"` 被當成目錄代碼傳進去,執行期才丟例外。**型別在這個介面上不設防**,
   呼叫點必須顯式 `codeForKind()`。T3 把繪製路徑改吃目錄時,同一類轉換點要逐個
   確認,不能靠 tsc 掃出來。

3. **破壞驗證的第一種做法本身是錯的。** 把某個品項的代碼改成與另一項重複,結果
   `requireCatalogItem` 在模組載入時就丟例外,整支 spec 連載入都失敗、顯示
   "No tests found" —— 那是紅,但紅在錯的地方,證明不了第 2 項在做事。改成**追加**
   一筆重複代碼的品項才隔離得出來。破壞驗證本身也要驗它壞對了地方。

**過渡橋:** `FurnitureKind` 與 `KIND_TO_CODE` 暫時留著。繪製路徑(2D、白模、
GLB、程序化、探針、快取)仍以 kind 當索引鍵,T3 換成 `code` 之後兩者一起刪。
`kindForCode` 查不到時回 `undefined` 並讓該件不繪製 —— 不要改成回預設值,那會
把「這條路徑還沒改吃目錄」變成畫錯東西。

**測試 fixture 的舊形狀會靜默失效。** `venue-furniture-models` M8 與 `plan-slots`
的存檔 fixture 帶的是 `kind` + `w`/`h`,沒有 `code`,3D 因此一件都不畫(M8 從
300 掉到 0)。這是 D8「舊存檔作廢」的預期行為,但值得記著:**平面圖的件數仍然
是 300**,只有 3D 是空的。使用者若讀進舊存檔,會看到 2D 有東西、3D 空無一物。


### T3 完成紀錄(2026-08-25)

實作完成,`tsc` 與 `eslint` 乾淨,新 spec `venue-catalog-drawing.spec.ts` 8 項
**單獨跑全綠**;合跑時隨機有 1–2 支紅,原因在下面第 4 點。

**做了什麼**

拆掉 T2 的過渡橋。2D、白模輪廓、GLB 分組與快取、程序化幾何、步驟 02/03 的探針
分組鍵、面板 testid,全部改以目錄代碼為鍵。`models.ts` 那份依 kind 索引的
`FURNITURE_MODELS` manifest 併進目錄的 `geometry` 欄位 —— 它是「同一件事有兩個
來源」的最後一處:目錄長出第十個品項時那份表不會跟著長,而畫面只會少一件家具,
沒有任何錯誤。`FURNITURE_DEFAULTS` 與 `kindForCode` 已刪除。`FurnitureKind` 與
`KIND_TO_CODE` 只剩 AI schema 那一條進入路徑在用,T4 一併刪。

程序化造型的 `BUILDERS` 改以 `ProceduralShape` 為鍵而不是品項:同一造型會被多個
品項共用(「接待櫃檯 100」與「接待櫃檯 150」是兩個代碼、同一種造型),以造型為鍵
之後新增尺寸變體不必動 builder。但**快取仍以代碼為鍵** —— 兩個尺寸變體共用造型
卻不共用幾何,以造型為鍵會讓後建立的那個拿到前一個的幾何。

**破壞驗證**

- 改目錄尺寸(接待櫃檯 1.4×0.5×1.6、桌子 2.4×0.9):2D 與步驟 02/03 的實際量測
  **同時**跟著變 —— 驗收第 4 項成立。
- 讓 3D 程序化路徑改讀寫死的 1.0/0.5/1.1:3 項轉紅(步驟 02 外廓、步驟 03 量測、
  探針分組)。

**四件規劃外的事**

1. **`tsc` 第三次沒擋住同一類錯誤。** `hasProceduralFurniture` 的參數從
   `FurnitureKind` 改成 `code: string` 之後,舊呼叫端傳 kind 依然編譯得過,只是
   永遠回 `false`。這是本輪第三次踩到「字串聯集對 `string` 相容」——
   T2 是 `createFurniture`,T3 是這一支。**代碼與 kind 之間的轉換點必須逐一手動
   確認**,型別不設防。

2. **探針的外廓量法第一版是錯的。** 取各零件包圍盒跨距的最大值,對多零件家具會
   低估:講台由三塊疊起來的板子組成,每塊自己只有幾公分厚,量出來是「講台高
   0.05m」。必須取各軸 min/max 的聯集。

3. **驗收第 2 項的字面要求對 GLB 品項不成立。** 「探針量到的實際 mesh 尺寸與
   catalog 宣告一致(誤差 < 1cm)」只有程序化品項做得到 —— 匯入模型只能等比縮放
   (AGENTS.md 硬規定),三軸不可能同時貼齊目錄框。正確的關係是「三軸都不超出,
   且至少一軸貼齊」,貼齊的那一軸就是限制縮放倍率的那一軸。spec 依此拆成兩項。

4. **驗收第 4 項沒有放進套件。** 它要求「改目錄尺寸後 2D 與 3D 同時變」,那需要
   在測試執行中改原始碼再等重建 —— 失敗時會把 repo 留在被改過的狀態。改成腳本化的
   破壞驗證(上面第一條),套件裡留的是它的靜態面:繪製路徑不得引用
   `FURNITURE_DEFAULTS` 或 `kindForCode`。

**結案(2026-08-25)**

上面留的「合跑穩定度」問題**沒有重現**。`venue-catalog-drawing.spec.ts` 在
6 輪不同組合下全綠:單獨跑 3 輪、與 7 支 3D 重量級 spec 合跑 1 輪、全套連跑
2 輪。spec 現有的 8 次重試 + `data-placing-code` 放置模式守衛已經夠用,沒有
再放寬預算。

**真正擋著 T3 結案的是另一件事,而且不是 flake:`ai-panel-persistent` 有 3 支
穩定紅。** T3 把 AI tool-call 的 fixture 從 `{ kind: "chair" }` 改成
`{ code: "CHR-45-90" }`,但 `src/lib/ai/tools.ts` 的 `add_furniture` schema 到
**T4** 才會換 —— handler 仍讀 `action.input.kind`。fixture 一改,
`codeForKind(undefined)` 查不到品項而丟例外,整個 `applyActions` 掛掉,
`ai-action-summary` 根本不會渲染,三個案例一起紅。

fixture 已改回 `kind` 並在該處註明「改 fixture 之前先改 schema」。T3 對該檔的
其餘三處改動(放置 testid、存檔欄位 `code`)是對的,保留。

免登入的 28 支 spec 最後結果:**256 通過、0 失敗**。`npm run lint` 與
`npx tsc --noEmit` 乾淨。

## 三、T9 範圍(2026-08-26 定案)

競品的「貼皮」有三項,使用者選定**只做第 1 項**。

### ✅ 採用:四面牆各自上傳貼圖

目前所有牆共用一組材質,改成 front / back / left / right 各自可選、可上傳。
第二輪 T8/T9 已經做出材質選擇器與上傳預覽(`SurfaceMaterials` +
`surfacePresets.ts`),這一項是把「一組」擴成「四組」,與既有決議沒有衝突。

**「四面」的定義已於 2026-08-26 定案:逐面牆各自設定。** 目前的牆是任意線段
(`WallSegment`),不是四面固定的牆 —— 使用者可以畫零面、三面、或八面牆;競品
是固定四面的盒子才有 front/back/left/right。備選方案是依牆的方位(法線朝北/南/
東/西)分成恆定四組,使用者選了**逐面牆**:畫面上列「牆 1、牆 2、牆 3……」,
點哪面改哪面。

因此:

- 材質設定**存在牆自己身上**,跟著 `WallSegment` 走。牆刪掉重畫,設定跟著消失
  —— 那是誠實的行為(那面牆真的不存在了),要寫進驗收而不是想辦法救回來。
- 沒有牆時清單是空的,分組 UI 不出現(條件 6 自然成立)。
- **柱子跟哪一組(條件 7)在這個模型下沒有現成答案** —— 逐面牆之後柱子沒有「所屬
  牆」,而第二輪已定「柱子不給獨立選項」。開工時的提案:保留**一份全域預設牆面
  材質**,新畫的牆與柱子都用它,個別牆可以覆寫。這樣柱子有明確歸屬,一面牆都沒
  畫的時候也還有東西可設定。這是 T9 唯一還沒拍板的細節,實作前會先確認。

### ❌ 不採用:家具本身可換材質

**與 D1/D4 直接衝突。** 家具是「租得到的型號」,材質該由品項決定,就像尺寸不可調
一樣 —— 開放換材質等於承認家具是「可自訂的道具」,會鬆動整輪的定位。要做的話是
在目錄裡加不同材質的品項(例如「木紋櫃檯」與「白色櫃檯」是兩個代碼),而不是給
使用者一個材質下拉選單。

### ❌ 不採用(這一輪):招牌/看板可上傳自己的圖

對展場是剛需(放 logo 與主視覺),但目前連「招牌」這個物件都還沒有 —— 要先在目錄
新增品項(平面看板,程序化造型很簡單),再讓它接上傳圖。**價值高但不屬於「貼皮」
的最小範圍**,另立 story 比塞進 T9 清楚。
