## R1 預設場地尺寸改為標準展位

**回饋原文**:一開始的預設場景,展場絕大多數的都是 3*3 / 3*6 / 3*9 / 6*6

**現況**:`src/lib/venue/plan.ts:21` `VENUE_SIZE_M = 50`;`createDefaultFloor()` 一律開 50×50m 方形。

**需求**:預設提供常見展位 3×3 / 3×6 / 3×9 / 6×6(公尺)供選,而非空白 50m 大場。

**待決**
- 做成「展位 preset 選擇器」(進 wizard 步驟 01 前或工具列),還是單純改預設地板尺寸?建議前者 —— 保留自訂多邊形能力。
- `VENUE_SIZE_M` 同時是「預設地板尺寸」與「預設視圖 fit 尺寸」,改預設會連動鏡頭。preset 需同時帶 fit 尺寸。
- 4 種以外是否允許自訂長寬輸入?

## R2 2D 選取物件顯示尺寸標註

**回饋原文**:希望 2D 平面圖柱子等被選取時可以出現他與邊邊的距離(附圖)

**參考圖語意**:總寬 2200cm、總高 600cm;柱子距左 1525、距右 525、距上 300、距下 150。紅色雙箭頭 + 數字,單位 cm。

**現況**:2D 畫布無任何距離標註。

**需求**:選取物件時,畫出該物件至場地四邊的距離標註,並標場地總寬高。單位 **cm**(內部維持公尺,顯示層換算)。

**待決**
- 標註對象只到「場地邊界」,還是也要到最近的牆/其他家具?圖上只有邊界 —— 建議先做邊界。
- 只有柱子,還是家具/牆同樣顯示?
- 旋轉過的家具怎麼量:用 AABB 還是實際旋轉後的邊?

## R3 牆高可調 4–6m

**回饋原文**:牆壁通常 4-6 米高

**現況**:`WALL_HEIGHT_M = 3` **硬編兩份** —— `src/components/venue/VenueScene.tsx:48`、`src/components/venue/RefinedScene.tsx:43`。違反 AGENTS.md「尺寸常數一律進 `src/lib/venue/`,不要在元件內寫死數字」。

**需求**:牆高預設改為 4–6m 區間內的值,並讓使用者可調。

**必要重構(非選項)**:常數搬進 `src/lib/venue/plan.ts`,兩個 3D 場景共用。

**待決**
- 全域一個牆高,還是 per-wall?建議全域(展場實務就是統一高度)。
- 預設值取多少(4?)、可調範圍與刻度。
- UI 放哪個步驟(步驟 01 工具列?步驟 02?)。

## R4 步驟 02 缺刪除家具入口

**回饋原文**:預覽 3D 場景的時候,家具沒有地方刪除

**現況**:刪除按鈕(`PlanToolbar` 的 `canDelete` / `onDelete`,`PlanEditor.tsx:975-982`)與 Delete/Backspace 鍵盤處理(`handleKeyDown`)**都只掛在 step 01 的 `step-edit` 容器**。步驟 02 可放置、可移動、可旋轉,唯獨不能刪。

**需求**:步驟 02 選取家具後可刪除(按鈕 + Delete 鍵)。

**注意**:`handleNextStep()` 目前**刻意**在進 step 02 前清空 `selectedObject`,理由寫在該處註解(防止殘留選取在 step 02 被誤刪)。這條要重新設計,不能直接拿掉那段。

## R5 步驟 02 家具顯示模型輪廓(不需貼圖)

**回饋原文**:預覽 3D 場景的時候,家具也應該看得當模型的形狀(不需要貼圖),而不是現在的方塊

**現況**:`VenueScene.tsx:400` 家具是 `<boxGeometry args={[item.w, height3d, item.h]} />` 純方塊。真實模型只在步驟 03。

**⚠ 這條推翻既有定調,需明確拍板**
- `stories/venue-refined-3d.md` 驗收條件寫死:「在步驟 02 停留時不載入步驟 03 專用的貼圖資源」。
- `playwright-tests/venue-furniture-assets.spec.ts` 的 C1–C3 三個案例就是在守「步驟 02 零 GLB 請求」。改了會紅,而且**是該紅**。

**技術路徑(成本不高)**
- 重用 `furnitureModels.tsx` 的 `normalizeModel()` 產出的 geometry,材質換成單色 `MeshStandardMaterial`,不載 WebP 貼圖。
- GLB 本身仍要下載(幾何在裡面),所以守衛必須從「零 GLB 請求」改寫成「零貼圖 / 零 PBR 資源請求」。
- 3 種程序化家具(counter / bannerStand / podium)已有幾何,直接共用。
- `furnitureModelStats.ts` 的依 kind 快取可跨步驟重用 —— 反而是加分。

**待決**:是否同意推翻上述定調與改寫測試?

## R6 步驟 03 材質可選 + 可上傳

**回饋原文**:第三步驟的時候,地板/牆壁要可以讓用戶自己選材質,進階一點可以讓他們自己上傳材質來預覽

**現況**:地板/牆/柱材質由 `src/components/venue/surfaceTextures.ts` **程序化 bake**(FLOOR_RES 1024 等),使用者無選擇權。

**需求**
- (a) 提供材質預設集,使用者自選地板 / 牆壁(/ 柱子?)。
- (b) 進階:使用者上傳自己的材質圖來預覽。

**待決**
- 預設集怎麼來?程序化參數化(改顏色/粗糙度/紋理型別)成本低;導入外部貼圖包則要處理授權與體積。
- 上傳走哪條路:
  - **client-only `URL.createObjectURL`** —— 不進後端、重整即失、零安全面。建議先做這條。
  - **存 Supabase Storage** —— 要新 `/api/*` route、檔案型別與大小驗證、RLS、配額。另立 story。
- 上傳的貼圖只有 baseColor,沒有 normal / roughness,而現有 PBR pipeline 假設有 normal map —— 要決定 fallback 行為。
- 柱子是否也開放?
