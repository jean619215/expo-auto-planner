# 場地規劃器使用者回饋(第二輪)—— 決議、任務順序與驗收標準

> **狀態:決策完成(2026-08-19),可開工。**
> 來源:使用者回饋 6 條。現況已對照當時程式碼查證,行號為當時狀態。

---

## 一、六條需求與決議

### R1 展位尺寸 preset

**回饋**:一開始的預設場景,展場絕大多數的都是 3*3 / 3*6 / 3*9 / 6*6

**現況**:`src/lib/venue/plan.ts:21` `VENUE_SIZE_M = 50`;`createDefaultFloor()` 一律開 50×50m 方形。

**決議**
- 做 **preset 選擇器 + 允許自訂長寬**。四種 preset(3×3 / 3×6 / 3×9 / 6×6,公尺)加自訂輸入。
- 換尺寸時若有物件會落在新場地外,**先彈確認對話框告知有 N 件會超出**;確認後才套用(超出者夾回場地內)。
- preset 需同時帶「預設視圖 fit 尺寸」—— `VENUE_SIZE_M` 現在同時扮演這兩個角色,拆開時不要漏。

### R2 柱子邊界距離標註

**回饋**:希望 2D 平面圖柱子等被選取時可以出現他與邊邊的距離(附圖:總寬 2200cm、總高 600cm,柱子距左 1525 / 右 525 / 上 300 / 下 150,紅色雙箭頭)

**現況**:2D 畫布無邊界距離標註(既有的只有柱子尺寸、牆長、地板邊長)。

**決議**
- 標註對象**只到場地四邊**,不做最近物件搜尋。
- **只有柱子**被選取時顯示(家具與牆不做)。
- 量的是**邊到邊**,不是中心到邊界。驗證方式:`左距 + 柱寬 + 右距 === 場地總寬`(參考圖 1525 + 150 + 525 = 2200)。
- 數字**可輸入**,用來精確定位柱子。
- **輸入框不受 `SNAP_M` 吸附限制**(可停在 1525cm 這種非 50cm 倍數的位置);拖拉仍照舊吸附 50cm。這是刻意的不一致 —— 拖拉要快、輸入要準。**必須在 UI 上讓使用者理解「輸入的精確值再拖一下就會被吸附掉」**,否則會覺得設定值無故消失。

### R3 牆高可調

**回饋**:牆壁通常 4-6 米高

**現況**:`WALL_HEIGHT_M = 3` **硬編兩份** —— `VenueScene.tsx:48`、`RefinedScene.tsx:43`。違反 AGENTS.md「尺寸常數一律進 `src/lib/venue/`」。

**決議**
- **全域一個牆高**(非 per-wall),`Wall` 型別不加欄位,AI tool schema 不動。
- **可調範圍 2–10m,預設 4m**。回饋說的「通常 4-6」是常態不是上限,硬夾在 4–6 會讓挑高場地做不了。
- 常數搬進 `src/lib/venue/plan.ts`,兩個 3D 場景共用 —— 必要重構,不是選項。
- 調整 UI 放**步驟 02(白模預覽)**,改高度當場看到 3D 結果。

### R4 步驟 02 刪除家具

**回饋**:預覽 3D 場景的時候,家具沒有地方刪除

**現況**:刪除按鈕(`PlanToolbar` 的 `canDelete` / `onDelete`,`PlanEditor.tsx:975-982`)與 Delete/Backspace 鍵盤處理都**只掛在 step 01 的 `step-edit` 容器**。步驟 02 可放置、可移動、可旋轉,唯獨不能刪。

**決議**
- 步驟 02 選取家具後可刪除(按鈕 + Delete 鍵)。
- **進入步驟 02 時仍清空選取**(維持 `handleNextStep()` 現有行為)。要刪就在 02 重新點一次,意圖明確、不會誤刪。那段防誤刪註解的前提改變了,但結論不變 —— 更新註解說明新理由,不要刪掉行為。

### R5 步驟 02 家具顯示模型輪廓

**回饋**:預覽 3D 場景的時候,家具也應該看得當模型的形狀(不需要貼圖),而不是現在的方塊

**現況**:`VenueScene.tsx:400` 家具是 `<boxGeometry args={[item.w, height3d, item.h]} />` 純方塊。

**決議:同意推翻既有定調。**
- 重用 `furnitureModels.tsx` 的 `normalizeModel()` 產出 geometry,材質換成單色 `MeshStandardMaterial`,**不載 WebP 貼圖**。
- `stories/venue-refined-3d.md` 的驗收條件「步驟 02 不載入步驟 03 專用的貼圖資源」需改寫。
- `playwright-tests/venue-furniture-assets.spec.ts` **C1–C3 三個守衛從「零 GLB 請求」改寫為「零貼圖請求」**。改寫後必須做破壞驗證(見第五節)—— 否則等於把守衛拆了卻沒補上。
- 3 種程序化家具(counter / bannerStand / podium)已有幾何,直接共用。
- `furnitureModelStats.ts` 的依 kind 快取跨步驟重用,是效能加分。

### R6 步驟 03 材質可選 + 可上傳

**回饋**:第三步驟的時候,地板/牆壁要可以讓用戶自己選材質,進階一點可以讓他們自己上傳材質來預覽

**現況**:地板/牆/柱材質由 `surfaceTextures.ts` **程序化 bake**(FLOOR_RES 1024 等),使用者無選擇權。

**決議**
- **兩種來源都要**:先做程序化參數化打底,再補幾款真實貼圖。**拆成兩個 task 依序跑,不混在一起。**
- 適用表面:**地板 + 牆壁**。柱子跟隨牆的材質,不給獨立選項。
- 上傳:**只做瀏覽器預覽**(`URL.createObjectURL`),不進後端、重整即失。存檔另立 story。
- 上傳圖只有 baseColor:**只當 baseColor 用,關掉凹凸感**(不自動推 normal map、不借用預設材質的 normal)。上傳的材質會比內建的平,但不會出現假的、對不上圖案的陰影。

## 二、跨需求共同決議

- **尺寸標註單位統一為公分**,依台灣建築圖慣例。這表示既有標註也要改:地板邊長「10.0 m」→「1000cm」、柱子「0.5 × 0.5 m」→「50 × 50cm」、牆「3.0 m」→「300cm」。`venue-dimensions.spec.ts` 有一批斷言直接比對這些字串,會一起失敗 —— 那是預期中的,要同步更新。獨立成一個 task(T3),不要跟新標註功能混在一起,否則測試失敗時分不清是單位改動還是新功能寫壞。
- **舊存檔直接作廢**。R1 / R3 / R6 會加欄位(展位尺寸、牆高、材質選擇),不做向後相容、不寫遷移函式。`serializePlanSnapshot` / `EMPTY_PLAN_BASELINE` 直接改。
- **`PlanEditor.tsx` 是唯一 state owner 且已約 1584 行**。本輪多個 task 都要往它加狀態,這也是全部依序執行(不平行)的主因。

## 四、驗收標準

每個 task 開工前先把這些寫成 Playwright 檢查項,**先讓它失敗**,實作後才通過。

### T1 牆高

1. 步驟 02 場景 `data-wall-height-m` 預設為 `4`
2. 調到 6 後,步驟 02 牆 mesh 實際高度 = 6(探針讀 geometry,不是讀 UI 回音)
3. 同一份值傳到步驟 03:`refined-scene` 的 `data-wall-height-m` 與步驟 02 相同
4. 柱子高度跟著牆高走(現況兩者共用同一常數)
5. 超出 2–10 範圍的輸入被夾制
6. `grep -rn "WALL_HEIGHT_M = " src/components/` 無結果(常數只在 `plan.ts`)
7. **破壞驗證**:把 `RefinedScene.tsx` 改回硬編 3 → 第 3 項應失敗

### T2 步驟 02 刪除

1. 步驟 02 放家具 → 點選 → 按刪除鈕 → `furnitureCount` 減 1
2. 同上流程改按 Delete 鍵 → 同樣減 1
3. 從步驟 01 帶著選取進步驟 02 → `selectedType()` 為 `""`
4. 步驟 02 未選取時刪除鈕 disabled,按 Delete 無效果
5. 刪除後回步驟 01,該家具確實不在(不是只有 3D 消失)
6. **破壞驗證**:移除 `step-preview` 的 `onKeyDown` → 第 2 項應失敗

### T3 單位改公分

1. `edgeLabels()` 回傳格式為 `"1000cm"` 而非 `"10.0 m"`
2. `columnLabel()` 為 `"50 × 50cm"`
3. `wallLabel()` 為 `"300cm"`
4. 數值換算正確:原 10.0m 顯示 1000cm(不是 100 或 10000)
5. 小數處理明確:0.5m → `50cm`,不出現 `50.0cm` 或 `49.999cm`
6. `venue-dimensions.spec.ts` 全部通過(斷言已同步更新)
7. 幾何未被改動:柱子 w/h、地板頂點座標的內部值仍是公尺,只有顯示層變

### T4 柱子邊界標註(唯讀)

1. 選取柱子 → `data-column-offsets` 為 `{left,right,top,bottom}`,單位 cm 整數
2. **`left + 柱寬 + right === 場地總寬`**(驗證量的是邊到邊,不是中心到邊)
3. 上下同理
4. `data-venue-size-cm` 恆顯示總寬高
5. 取消選取 → `data-column-offsets` 消失
6. 拖曳柱子後數值即時更新
7. 選家具/牆時**不**出現此標註
8. 既有 `venue-dimensions.spec.ts` 全部仍通過
9. **破壞驗證**:offset 改成中心到邊界 → 第 2 項應失敗

### T5 可輸入定位

1. 輸入 `1525` → `data-column-offsets.left === 1525`(**不被吸附成 1500**)
2. 柱子實際位置對得上該值
3. 設定 left 後 right 自動 = 總寬 − 柱寬 − left
4. 輸入超出邊界的值 → 夾到合法範圍,柱子不出界
5. 輸入後**拖曳一次** → 吸附回 50cm 倍數(拖曳行為未被破壞)
6. 輸入非數字/負值 → 拒絕,柱子不動
7. **破壞驗證**:輸入路徑接上 `snapToGrid` → 第 1 項應失敗

### T6 展位 preset

1. 選 3×6 → 地板為 3×6 矩形,頂點數 4
2. 視圖 fit 到新尺寸(`pxPerMeter` 隨之改變)
3. 自訂輸入 4×7 → 同樣生效
4. 場上有 2 件物件會超出時,換尺寸跳確認對話框且**顯示件數 2**
5. 對話框取消 → 尺寸與物件皆不變
6. 對話框確認 → 尺寸改變,超出物件被夾回場地內
7. 無物件超出時**不**跳對話框
8. 尺寸進存檔,讀檔後還原
9. **破壞驗證**:拿掉超出偵測 → 第 4 項應失敗

### T7 步驟 02 家具輪廓

1. 步驟 02 六種有 GLB 的家具,geometry 三角面數 > 12(box 是 12)
2. 步驟 02 與步驟 03 的 `partCount` 逐 kind 相同(同一份幾何)
3. 步驟 02 材質 `map === null` 且 `normalMap === null`(單色,零貼圖)
4. **步驟 02 網路請求中 `.webp` 數為 0**(C1–C3 改寫後的新形式)
5. 步驟 02 允許 `.glb` 請求(舊守衛的反向)
6. 步驟 02 → 03 往返後 `totalBuilds` 不增加(快取跨步驟重用)
7. 三種程序化家具在步驟 02 仍正常
8. **破壞驗證**:給步驟 02 材質掛上貼圖 → 第 3、4 項應失敗

### T8 材質選擇器

1. 步驟 03 有地板與牆兩組選單,各 ≥ 3 個選項
2. 切換 → 探針回報 `totalBakes` +1,材質參數改變
3. 切回原選項 → `totalBakes` **不**增加(快取生效)
4. 柱子跟隨牆的材質
5. 選擇進存檔,讀檔還原
6. 步驟 02 不受影響(不載步驟 03 材質)
7. **破壞驗證**:繞過快取 → 第 3 項應失敗

### T9 上傳材質預覽

1. 上傳 PNG → 地板 baseColor 來源標記為 `upload`
2. **`normalMap === null`**(關凹凸)
3. 上傳非圖片檔 → 拒絕 + 顯示錯誤,材質不變
4. 超過大小上限 → 拒絕 + 錯誤
5. 重整頁面 → 回到預設材質(刻意不持久)
6. 無任何 `/api/*` 請求(純前端)
7. **破壞驗證**:自動推 normal map → 第 2 項應失敗

### T10 真實貼圖包

1. `ATTRIBUTION.md` 存在,每個貼圖有來源與授權
2. 貼圖檔實際存在、格式 webp、單檔小於上限
3. 選單出現這些選項且套用後畫面改變
4. 全部同源(零外部下載,比照步驟 03 既有硬規定)

### 全域回歸閘(每個 task 都要過)

- `npm run lint` 通過
- 既有測試全部通過,除 5 支需帳密的(`ai-panel` / `membership-task7-task9` / `points-shop` / `profile-edit-mode` / `site-header`)
- `venue-refined-acceptance.spec.ts` 的往返快取檢查不退化

## 五、品質把關:破壞驗證

**問題**:測試通過不代表它在守什麼。選擇器打錯、屬性永遠是 `undefined`、比對永遠成立 —— 這種「空守衛」照樣通過,而且看起來跟真的一模一樣。

**做法**:實作完、測試通過之後,**故意把實作改壞一次**,確認對應的檢查項真的會失敗。會失敗代表它真的在守;仍然通過代表它是廢的,重寫。改壞的部分驗完立刻還原。

**本專案既有前例**
- `venue-refined-3d` task 4:刪掉 `table.glb`,確認 GLB 完整性檢查從 200 變 404
- `venue-refined-3d` task 7:停用模型快取,確認 `totalBuilds` 從 6 跳到 18(StrictMode 雙重建置 × 3 趟往返)

**本輪特別注意**:T7 是把既有守衛拆掉重寫(從「零 GLB 請求」改成「零貼圖請求」)。這種情況不做破壞驗證,等於守衛消失而沒人發現。
